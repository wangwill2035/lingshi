# 梦幻西游灵饰摆摊管理工作流程指导

## 工作内容总览

五大模块：
1. **品类管理** — 16个灵饰品类的名称、等级、部位映射维护
2. **价格管理** — 成本价、销售价、毛利率，调价留痕
3. **库存管理** — 入库、上架、中途核查、日结盘点
4. **销售报表** — 按品类汇总销量/销售额/成本/毛利，日报生成
5. **回款管理** — 回款登记、未回款跟踪、点卡回款区分

## 二、双轨库存逻辑

库存和在售两个数据独立维护，互不干扰：

- **入库（I）**：只增加库存商品，不影响在售
- **上架（O）**：库存减少N件，在售增加N件
- **销售**：在售减少，通过"应有在售 - 实际在售"反推得出
- **中途核查（C）**：对比系统应有在售与实际在售，差额=销售数量

## 三、二维码扫码规范

### 3.1 文本格式

文本共43个字符：`MMDDHHMMSS`（10位时间戳）+ `I/O/C/E`（1位操作符）+ `32位数字`（每两位对应1个品类数量，共16个品类）

### 3.2 操作符定义

| 操作符 | 含义 | 完成后展示 |
|--------|------|-----------|
| I | 入库 | 入库前后库存明细对比表格 |
| O | 上架 | 上架前后在售明细对比表格 |
| C | 中途核查 | 销售数量及金额明细表格 |
| E | 日结 | 全天销售数量及金额总结表格 |

### 3.3 解析工具（强制）

**必须使用parse_qr.py脚本解析，禁止手动数字分组**：
```
python <skill目录>/scripts/parse_qr.py --text "<扫码文本>" --human --all
```

### 3.4 扫码日志表结构（严格按列写入，逐行落表）

| 列 | 字段 | 格式要求 |
|---|------|------|
| A | 账面日期 | 纯日期 YYYY-MM-DD（22:00后归次日） |
| B | 发生日期 | 完整时间戳 YYYY-MM-DD HH:MM:SS |
| C | 操作符 | 单字母 I/O/C/E，不写中文 |
| D | 扫码原文 | 完整43位扫码字符串，必须原文记录 |
| E | 明细信息 | 人读汇总文本 |
| F | 发生数量 | 纯数字，不写文本格式 |

**写入要求**：禁止批量二维数组写多行文本（会静默失败），逐行单独写入；写完回读校验关键字段（D列原文必须存在、B列必须带完整时间）。

## 四、各操作详细流程（标准动作）

### 4.1 入库（I）—— 两步

1. parse_qr.py解析扫码文本
2. 写扫码日志（1行）
3. **入库明细表**：非零品类逐条写（发生日期 | 账面日期 | 名称 | 部位 | 等级 | 数量）
4. 更新**即时库存矩阵**
5. 同步本地工作台json（供网页端展示）
6. 展示入库前后库存对比表格

### 4.2 上架（O）—— 试算+四步

1. parse_qr.py解析
2. **先试算**：即时库存对应格子 - 上架数量，有负数 → 停止，向用户提问
3. 库存够则写扫码日志
4. **上架明细表**：非零品类逐条写
5. **入库明细表**同步写负数量记录（上架5件就写-5）
6. 更新**即时库存矩阵**（加负数自然减少）
7. 更新**即时在售矩阵**
8. 同步本地工作台json（供网页端展示）
9. 展示上架前后在售对比表格

### 4.3 中途核查（C）

时间窗口：8:00-21:00（夜间22:00后算次日）

1. parse_qr.py解析实际在售数
2. 反推销售：应有在售 - 实际在售 = 各品类销售数量
3. 写扫码日志
4. **销售明细表**：有销售的品类逐条写（10列：发生日期|账面日期|名称|部位|等级|数量|单价|金额|毛利率|毛利润）
5. 更新**即时在售矩阵**为实际数
6. 同步本地工作台json（含provisional截止时间、当日销售额、已售明细）
7. 展示销售明细表格
8. **连带展示回款情况**：当日销售额、已回款、未回款余额

### 4.4 日结盘点（E）

时间：每日22:00

1. parse_qr.py解析
2. 写扫码日志
3. 反推全天累计销售，按品类逐条写销售明细
4. 创建「日报-MM-DD」sheet，格式参考日报-11-06：
   - 库存变动表（16品类逐行：期初在售|期初库存|今日入库|今日上架|今日销售|期末在售|期末库存）
   - 销售毛利表（各品类销量/销售额/成本/毛利/毛利率）
   - 综合毛利率 = 总毛利 ÷ 总销售额
   - 底部汇总：总销量、总销售额、总回款、点卡回款、未回款、汇率
5. 重置本地工作台json（当日数据清零，准备次日）
6. 展示全天总结表格 + 连带回款汇总
7. **明细表不清空**：历史流水持续累积，按天追加（11-08清空是临时修复，以后正常不清）

### 4.5 回款

1. 写回款记录（发生日期+时间+金额+类型+备注+账面日期）
2. 同步本地工作台json（回款history数组）
3. 未回款 = 当日销售额 - 正常回款部分
4. 超出部分记为"点卡回款"，不冲减应收

### 6.3 飞书写入强制规范（血泪教训固化）
1. **sheet-id必须用英文id**：所有写入必须用表对应的英文sheet-id（如1eXNsG），绝对不能用中文表名当sheet-id，否则静默写入失败不报错
2. **逐行写入**：所有文本明细行必须一行一行单独写入，禁止批量二维数组一次写多行文本，会静默失败
3. **矩阵写入例外**：纯数字二维矩阵（库存/在售）可以直接传纯数字二维数组写入，但不要修改cells-get返回的单元格对象再写回
4. **写入前读表头**：每次追加记录前先回读当前表头列顺序，禁止凭记忆写列位置
5. **写后回读校验**：写完后读回最后一行确认数据真的落表，不能以为命令执行了就等于写成功
6. **行号确认**：追加前先读当前最后一行位置，不能凭记忆累加行号
7. **上架双轨流水**：上架操作除了写上架明细，必须同步在入库明细写负数量记录，保持库存流水完整
8. **盘点差异落表**：C/E盘点出来的差异=销售，必须逐行写入销售明细，写完回读确认，禁止批量写入
9. **日报汇总铁律**：日报分品类数据必须从销售明细sheet逐行SUM汇总，禁止凭记忆、估算或口算填写
10. **扫码日志固定列**：A列纯账面日期（YYYY-MM-DD）、B列完整发生时间（YYYY-MM-DD HH:MM:SS）、C列单字母操作符I/O/C/E、D列完整43位扫码原文、E列明细串、F列纯数字数量
11. **未回款口径**：未回款 = 累计销售额 - 累计回款总额，不是直接累加回款数
12. **扫码前置检查**：扫码得到42位少一位时，先切英文输入法重扫，不怀疑程序或扫码枪硬件
13. **输入法方案**：放弃Win11后台脚本自动切英文（被系统拦截不生效），扫码前手动切英文
14. **调价分段执行**：调价日分两段，调价时间点之前的历史销售不回溯改价，之后所有I/O/C/E按新价；prices.json、cost.json、parse_qr.py、面板stock/storage四处同步更新
15. **连扫I+O库存零效果**：连续扫同数量I入库+O上架票（新货直接上架）时，库存矩阵净效果不变无需写回，只更新在售矩阵；两票签名分别登记
16. **回款随时登记**：当日多笔回款随时登记，回款sheet逐行写，cash.json history数组追加，未回款=当日销售额-累计回款，多回部分自动记点卡口径
17. **E类无新增销售直接settled**：日结E盘值与当日最后一张C盘实盘值完全一致时，销售明细不新增，直接标记settled=true
18. **打印工具边界**：只改纯逻辑（DoReset只清16格数量、不强制切回入库标签），所有自绘按钮/Tab样式改动全部回退，EXE由用户本地编译替换，本环境不做UI自绘改动

## 十、错误处理约定

1. 口算加法错误 → 禁止口算，所有汇总用工具计算
2. 回款计算错误 → 点卡回款不能抵扣销售额，只能用正常回款部分冲减应收
3. 库存不够上架 → 先试算，不足时主动提问，不硬落表
4. 撤回入库 → 连带检查哪些上架依赖了该入库，避免库存变负
5. 扫码长度不对 → 提醒用户少一位，不猜测补全
6. 工作台数据不更新 → 每次飞书操作后必须同步刷新本地json，保证网页工作台实时显示
7. **追加写入错位** → 每次写明细表前必须先读最后一行位置，确认行号后再追加，绝不凭记忆累加行号（防止覆盖历史数据）

## 十二、2026-11-12 新固化规范（本地SQLite改造版）

1. **业务顺序硬约束**：必须先扫C/E盘点票算出当日销售额，再登记回款；禁止先回款后盘点，否则未回款会算出负数。
2. **扫码弹窗标准**：I/O/C/E扫完必须弹结构化明细：

## 十三、2026-11-13 原生C++工作台开发固化规范
1. **Win32中文开发规范**：所有原生窗口API必须使用宽字符W系列（CreateWindowExW/DefWindowProcW），字符串全部用L""宽字符前缀，禁止使用ANSI A系列API，彻底避免中文乱码

## 十四、2026-11-14 业务日期分界规则修正
- 核心规则：以E票日结为唯一跨天分界，不按自然日0点、也不按22点整点自动跳天
- 执行口径：
  1. 没扫E票之前，不管几点（哪怕到凌晨），所有I/O/C操作、回款都算当天
  2. E票本身算当天的日结，是当天最后一笔（通常在每天22:00-22:15之间扫完E票完成日结）
  3. E票扫完之后，后面所有新扫的票、回款，全部自动归到第二天
- 触发场景：避免深夜扫日结票被错算成第二天，导致当日日报数据分裂

## 二十、撤票（回滚）标准作业流程

工作中难免扫错/盘错，撤票一律按本节流程核对库表执行；未实现网页撤票功能前，不允许凭记忆直接改库。

### 20.1 通用步骤（任何票型先按此走）

1. **定位目标票**：按业务日、时间、操作符、明细串确认要撤的票；盘点票连带其 SUMMARY 汇总条（`C_SUMMARY` / `E_SUMMARY` / `E_DAY_SUMMARY`）一起处理。
2. **先备份数据库**：复制 `mhxy.db` 为 `mhxy.db.bak-rollback-YYYYMMDD-HHmmss`，确认备份落盘后再动手。
3. **反推应有状态**：盘点票按「上一张盘点票实盘 + 其后所有 O 票上架增量」反推在售；入库/上架票按流水反向推库存、在售。
4. **列撤销清单经用户确认**：写明删哪些明细/日志、库存与在售各恢复到什么值、哪些不动；用户确认后才落库，不擅自撤。
5. **事务内执行**：删对应明细与日志、反向恢复矩阵；一次事务提交，中途异常整体回滚。
6. **回读验算**：件数/金额闭合、库存合计、在售合计、流水条数逐一核对；再调 `/data` 接口复核前端显示与库一致。
7. **撤 E 票**：按 17.2 明确提示「当天尚未日结」，需重新扫 E 票定稿；旧的当日总销售汇总条一并删除，不残留。

### 20.2 分票型撤销口径

| 票型 | 删除明细 | 库存 storage | 在售 onsale | 备注 |
|------|----------|--------------|-------------|------|
| I 入库 | in_detail 正数量记录 | 按入库量减回 | 不动 | 先检查后续上架是否依赖该批入库，避免库存变负 |
| O 上架 | out_detail + in_detail 负数量记录 | 按上架量加回 | 按上架量减回 | 双向流水都要删，不能只删一边 |
| C/E 盘点 | sale_detail 本轮差额 + 主票 + SUMMARY | 一行不动 | 按上一张盘点实盘 + 其后 O 增量恢复 | 口径见 17.1；撤 E 票按 17.2 |
| 回款 | cash_log 对应记录 | 不动 | 不动 | 未回款、点卡回款口径随之重算 |

### 20.3 回读验算清单

- 被删明细、日志确已不存在，无残留 SUMMARY 汇总条。
- 今日销售件数/金额 = 剩余 sale_detail 汇总，金额闭合。
- 库存合计、在售合计与反推值一致，无负库存。
- `/data` 前端显示与库内一致。
- 备份文件路径记录在案，必要时可从备份回退。

### 20.4 网页撤票（一期已上线：仅 I/O）与二期方向

**一期已上线（2026-11-22）**：
- **开放范围**：仅入库 I、上架 O 票可在工作台流水列表点「撤销」；C/E 盘点票与汇总条不显示撤销按钮。
- **撤销链路**：点撤销先跑只读预检（列出逐品类库存/在售前后值）→ 二次确认弹窗 → 撤前自动备份数据库 → 事务内反向冲销库存/在售、删除对应明细与主票日志 → 提交后回读验算，负库存/负在售兜底校验。
- **拦截与警告**：撤后库存或在售会变负则拒绝并说明原因；若该票之后已有入账/盘点记录，弹窗警告「后续盘点需重新扫描核对」。
- **C/E 口径**：C/E 盘点票网页暂不支持撤销，仍按 20.1–20.3 由助手核对库表处理。

**二期待办（本期不实现）**：

- 网页撤票落地前未覆盖的票型，撤票一律按 20.1–20.3 由助手核对库表执行，不凭记忆直接改库。
